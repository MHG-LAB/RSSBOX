多平台架构对比

一、Android

分层：Linux 内核 → HAL 硬件抽象层 → 系统运行库层（ART、Bionic libc、OpenGL ES/Vulkan、Media）→ 应用框架层（AMS/PMS/WMS、View 体系、ContentProvider）→ 应用层。

核心机制

  • 运行：Zygote 进程预加载后 fork 出应用进程，.dex 经 ART 做 AOT + JIT 混合编译成 oat，按使用热度分层编译。
  • IPC：Binder 一次拷贝（mmap 映射内核缓冲区），C/S 架构，AMS、WMS 等系统服务全靠它跨进程。
  • 线程：主线程 Looper + MessageQueue + Handler 消息循环，Choreographer 对齐 VSYNC 驱动“输入 → 动画 → 测量布局绘制”三段流水。
  • 渲染：View 树三大流程 Measure / Layout / Draw，绘制指令进 RenderThread，最终交给 SurfaceFlinger 合成。Measure 因 wrap_content 与 weight 常出现二次测量，是性能老话题。
  • 更新范式：命令式、可变 UI。Compose 改成了声明式：组合 → 布局 → 绘制，Snapshot 状态系统 + SlotTable 存储，重组按作用域局部失效，接近“单趟布局”。

架构范式：四大组件 + Intent 解耦，MVVM/MVI + Repository + 单向数据流，Hilt/Koin 注入，Coroutines/Flow 处理并发，Gradle 多模块 + feature module 做物理隔离。

二、iOS

分层（官方四层）：Core OS（Darwin/XNU、文件系统、安全）→ Core Services（Foundation、CoreFoundation、CoreLocation）→ Media（Core Graphics、Core Animation、AVFoundation）→ Cocoa Touch（UIKit、SwiftUI）→ 应用层。

核心机制

  • 运行：ObjC 是动态派发（objc_msgSend 走方法缓存 + 消息转发），Swift 静态派发为主，协议走 witness table，泛型走 specialization；两者可混编。
  • 进程：每 App 独立沙盒进程，Mach port / XPC 通信，App 间不能直接访问数据（比 Android 的共享存储更封闭）。
  • 线程：主线程 RunLoop 驱动；GCD 是队列模型而非线程模型（串行/并发队列 + QoS 调度到线程池）；Swift Concurrency 用 async/await + actor 隔离可变状态。
  • 渲染：UIView 只是 CALayer 的代理，真正渲染在独立的 Render Server（backboardd）进程完成，Core Animation 提交 layer 树后由它合成上屏——这也是 iOS 动画顺滑的结构性原因。
  • 内存：ARC 编译期插桩引用计数，无 GC 停顿，代价是循环引用要手动 weak/unowned。

架构范式：MVC 是历史主线，实际工程多用 MVVM / Coordinator / 单向数据流（Combine 或 AsyncSequence），模块化走 SPM / CocoaPods；SwiftUI 是值类型 + 协议的声明式体系，依赖 Environment 注入，状态用 @State/@StateObject 分层持有。

三、Vue

三层：响应式系统（Reactivity）+ 运行时（Runtime）+ 编译器（Compiler）。这是 Vue 和 React 最根本的分野——Vue 有编译器参与优化，React 靠运行时调度。

核心机制

  • 响应式：Vue 3 用 Proxy 拦截读写，effect 做依赖收集（track/trigger），组件渲染函数就是一个 effect，数据变了自动重跑。
  • 更新：虚拟 DOM + 编译期 PatchFlag 标记动态节点，Block Tree 把静态节点踢出 diff，实现“靶向更新”；更新进微任务队列（nextTick）批处理，一次事件循环只刷一次。
  • 组件：Options API 或 Composition API（setup），props 下传、emit 上传；composable 是复用单元，替代了 mixin。

架构范式：官方全家桶分工明确——Vue 管视图、Vue Router 管路由、Pinia 管状态、Vite 管构建、Nuxt 管服务端。分层通常是视图 / 业务 composable / 数据访问，provide-inject 做跨层依赖。

四、React

三层（React 18） ：Scheduler 调度器 + Reconciler 协调器 + Renderer 渲染器。Renderer 可插拔（react-dom、react-native、自研渲染器），这是 React 能一套内核跑多端的原因。

核心机制

  • Fiber：把渲染任务拆成链表结构的 Fiber 节点，双缓存（current / workInProgress）交替，render 阶段可中断可恢复，commit 阶段一次性提交不可中断。
  • 调度：Lane 模型标优先级，时间切片把长任务切进 5ms 片，高优先级更新（如输入）可插队并丢弃旧的低优先级工作。
  • Hooks：函数组件 + 闭包，状态挂在 Fiber 上按链表顺序匹配，所以顺序不能变、条件里不能写。
  • 更新流程：setState → 调度 → render（可中断 diff）→ commit（DOM 变更 + layout effect）→ passive effect。

架构范式：只提供内核，其余全靠社区组合——Router、状态（Redux/Zustand）、构建（Vite）、元框架（Next.js）。单向数据流 + 不可变数据，容器/展示分离，Suspense 把异步数据也纳入渲染流程。

五、Flutter

三层：Framework（Dart：Widgets / Material / Cupertino / Rendering / Animation / Painting）+ Engine（C++：Skia 或 Impeller、Dart VM、文字排版、平台通道）+ Embedder（各平台原生壳，负责窗口、生命周期、输入）。

核心机制

  • 三棵树：Widget（不可变配置）→ Element（生命周期与状态宿主）→ RenderObject（布局绘制）。Widget 每帧重建很便宜，Element 才持有状态，RenderObject 才真正干活。
  • 布局：约束向下传递、尺寸向上回传，单趟遍历完成（one-pass layout），不像 Android 可能测两次；代价是尺寸不能反向依赖子节点，必须靠 LayoutBuilder这类手段破例。
  • 渲染：自绘引擎，不走系统控件，直接 Skia Canvas 出 GPU 指令；Impeller 用预编译 shader 彻底解决首帧 jank。所以三端视觉完全一致，但包体和控件“非原生感”是代价。
  • 线程：UI 线程跑 Dart 主 isolate，Raster 线程负责光栅化，IO 线程做解码；isolate 间无共享内存，只靠 SendPort 传消息。
  • 热重载：JIT 增量编译 + Element 树状态保留，改代码不丢页面状态。

架构范式：状态管理官方只给 InheritedWidget/Provider，社区 Riverpod / Bloc / GetX 三分天下；跨原生走 MethodChannel / EventChannel / FFI；分层一般是 presentation / domain / data + Repository。

六、React Native

核心机制：这里必须分老架构和新架构讲，否则结论会过时。

老架构（Bridge）

  • 三线程：JS 线程、Shadow 线程（算 Yoga 布局）、UI 主线程。
  • 通信全靠 Bridge：消息序列化成 JSON 异步批量过桥，异步意味着“一次跨桥一次延迟”，列表滚动时最容易被卡住。
  • 布局用 Yoga（C++ 实现的 Flexbox），也是单趟约束求解，和 Flutter 思路同源。渲染是原生视图——RN 渲染的是真 UIButton，不是自绘。

新架构（已稳定）

  • JSI：C++ 层直接持有 JS 对象引用，可以同步调用宿主能力，Bridge 的序列化瓶颈被拆掉。
  • Fabric：新渲染器，Shadow Tree 用 C++ 实现并由 JS 与原生共享，支持并发渲染与优先级插队。
  • TurboModules：原生模块懒加载 + 类型安全，Codegen 从 TS 定义生成 C++ 胶水代码。
  • Hermes：默认引擎，预编译字节码，启动快、内存低，代价是缺 JIT。

架构范式：组件模型与 React 完全同构（Hooks、单向数据流），差异只在宿主组件和原生模块这层；工程上常配 React Navigation + Redux/Zustand，原生侧仍需写 Kotlin/Swift 模块兜底。

一句话归纳

  • Android / iOS：系统级分层 + 强约束的 IPC 与渲染管线，性能天花板高但平台绑定死。
  • Vue / React：都是“声明式 + 差分更新”，Vue 把优化前移到编译器（编译期标记 + 精确依赖追踪），React 把优化后移到运行时调度（可中断、按优先级）；选型本质是“编译期确定性”和“运行时灵活性”的取舍。
  • Flutter / RN：跨平台的两条路线——Flutter 自绘统一，一致性和性能可控但脱离原生控件；RN 渲染原生，原生感强但依赖桥接效率，新架构用 JSI + Fabric 把桥的异步瓶颈填平。
