MIT 6.S081 操作系统工程：Lab4-Traps实验笔记

MIT 6.S081 Lab4 笔记：backtrace 与 alarm 的实现与避坑

个人学习记录，代码仅供学习参考，请勿直接用于课程作业提交。

环境：Windows 11 + WSL2（Ubuntu 24.04），riscv64-linux-gnu 工具链 + gdb-multiarch。

Lab4 包含三部分：RISC-V 汇编问答、backtrace 和 alarm。任务数量不多，但涉及内核栈布局、trapframe、系统调用约定和定时器中断等多个机制，边界条件比较密集。

本文先梳理 backtrace 与 alarm 的实现思路，再总结实现过程中容易出现的错误。

一、Lab4 要做什么

任务验收

三个部分可以概括为：

  • RISC-V assembly：阅读 user/call.asm，回答 6 个关于参数寄存器、内联优化、端序和可变参数的问题；
  • Backtrace：沿 s0（fp）链遍历内核栈，读取每个栈帧固定偏移处的返回地址；
  • Alarm：定时器中断到期时把 trapframe->epc 改到 handler；sigreturn 时用提前备份的 trapframe 整体恢复用户现场。

二、RISC-V assembly（Part 1）

Part 1 要求阅读 user/call.c 及其反汇编 user/call.asm，回答 6 个问题。题目代码：

int g(int x) { return x+3; }
int f(int x) { return g(x); }
void main(void) {
  printf("%d %d\n", f(8)+1, 13);
  exit(0);
}

汇编中的地址与具体构建相关。下文数值来自实验提交时的 call.asm，更换工具链或重新链接后可能不同。

1. 哪些寄存器存放函数参数？

RISC-V 使用 a0-a7 传递函数参数。main 调用 printf 时：a0 是格式串地址，a1 是 f(8)+1（被常量折叠为 12），a2 是 13。因此 13 存放在 a2。

24: 4635        li a2,13
26: 45b1        li a1,12
30: 00000097    auipc ra,0x0
34: 600080e7    jalr 1536(ra)     # 630 <printf>

2. main 中调用 f 和 g 的代码在哪里？

main 中没有对 f 或 g 的调用。编译器做了两层优化：g 被内联进 f，f 又被内联进 main，并且 f(8)+1 被常量折叠为 12。f 和 g 仍然作为独立函数存在于二进制中（它们不是 static），只是 main 没有调用。

3. printf 的地址是多少？

0x630，见 jalr 指令后的注释 # 630 <printf>。

4. 执行 jalr 跳到 printf 后，ra 的值是多少？

0x38。jalr 位于 0x34，硬件会把下一条指令的地址写入 ra；printf 的序言会把这个返回地址保存在自己的栈帧中，函数返回时使用。

5. printf("H%x Wo%s", 57616, &i) 输出什么？

  • 57616 的十六进制是 0xE110；
  • i = 0x00646c72，小端序下内存中的字节为 72 6c 64 00，%s 从低地址逐字节读取，得到 rld。
运行环境输出
xv6 的 printf（数字表为大写）HE110 World
glibc 的 printf（小写）He110 World

注意输出中是数字 110，不是字母 ll0。

如果换成大端序：要保持 rld 的输出，i 应设为 0x726c6400；57616 不需要修改，因为 %x 打印的是整数值，与内存字节序无关。

另外，xv6 的 printf 不支持宽度和补零，%02x 不能用于逐字节验证；可以使用 GDB 的 x/4bx &i。

6. printf("x=%d y=%d", 3) 在 y= 后面打印什么？

不确定。a1 是第一个可变参数，值为 3，第一个 %d 取到 3；第二个 %d 从 a2 取值，但调用者没有传第二个参数，a2 中是上一条指令或上一次调用遗留下来的数据，每次运行都可能不同。可变参数超过寄存器容量（a1-a7，共 7 个）后才会从栈上取，printf 同样不会检查实际参数个数。

小结

  • 参数寄存器：a0-a7，13 在 a2
  • f / g 调用：被内联并常量折叠，main 中没有调用指令
  • printf 地址：0x630（本次构建）
  • jalr 后的 ra：0x38
  • 大小端输出：HE110 World（xv6，大写）/ He110 World（glibc）
  • 参数不足：读取 a2 的残留值，结果不确定

二、Backtrace：沿 fp 链走内核栈

1. 栈帧布局：fp-8 是返回地址，fp-16 是上一帧

内核使用 -fno-omit-frame-pointer 编译，每个函数都有标准序言：

addi sp, sp, -16     # 开帧
sd   ra, 8(sp)       # 返回地址 → fp-8
sd   s0, 0(sp)       # 调用者的 fp → fp-16
addi s0, sp, 16      # s0 = 帧顶 = 进入函数时的 sp

布局如下：

高地址
      ┌───────────────┐ ← fp（s0）= 调用者的 sp
      │  fp-8:   ra   │   返回地址（jalr 的下一条指令）
      │  fp-16: 旧 fp │   调用者的 s0，即上一帧 fp
sp →  ├───────────────┤
      │  局部变量 ... │
低地址

因此回溯只需要两步：读 *(fp-8) 得到返回地址，读 *(fp-16) 得到上一帧 fp。

叶子函数（内部不调用其他函数）可能省略 ra 的保存，上述约定不成立；但 backtrace ← sys_sleep ← syscall ← usertrap 这条链上都是非叶子函数，不受影响。

2. 停止条件：内核栈只有一页

kernel/memlayout.h 中：

#define KSTACK(p) (TRAMPOLINE - ((p)+1)* 2*PGSIZE)

每个进程预留两页，低的一页是未映射的守护页，高的一页才是真正的栈，大小为 4096 字节，即 4KB。栈从页顶向下生长。

走到最顶上的 usertrap 帧时有两个关键事实：

  • 它的 fp 恰好等于 kstack + PGSIZE（页顶，页对齐）；
  • 它 fp-16 处的"旧 fp"其实是用户态的 s0——usertrap 是从 trampoline 的 jr t0 跳进来的，不是被 jalr 调用的。

因此停止条件是：记录最初 fp 所在的页 PGROUNDDOWN(fp)，每走一步检查当前 fp 是否仍在该页，离开即停止。

这也解释了为什么恰好打印 3 个地址：

帧fp-8 中保存的值addr2line 显示
backtrace返回进 sys_sleepkernel/sysproc.c
sys_sleep返回进 syscallkernel/syscall.c
syscall返回进 usertrapkernel/trap.c
usertrap用户 ra（无效）不打印，循环停止

3. 实现

在 kernel/riscv.h 中添加读取 s0 的函数。必须放在 #ifndef __ASSEMBLER__ 内部，原因见第四节：

static inline uint64
r_fp()
{
  uint64 x;
  asm volatile("mv %0, s0" : "=r" (x) );
  return x;
}

实现要点：

  • 使用 %p 打印：grade 的正则只匹配行首 0x000000008...，%x 不满足要求；
  • 先打印 *(fp-8)，再更新 fp = *(fp-16) ，顺序相反会漏掉 sys_sleep 那一层；
  • 输出第一行先打印 backtrace:。

之后需要三处配套修改：kernel/defs.h 添加原型、sys_sleep() 开头调用、panic() 中调用。

三、Alarm：定时器、trapframe 与 a0

1. 数据结构：五个字段

int interval;                 // 用户传入的 tick 间隔，0 表示关闭
uint64 handler;               // handler 的用户地址
int ticks;                    // 已计 tick 数
int in_handler;               // 是否正在执行 handler（防重入）
struct trapframe saved_tf;    // 被打断时的用户现场副本

在 allocproc() 中初始化：

进程槽位会复用，不初始化会残留上一个进程的状态。

2. sigalarm：只记录参数

  • n 用 argint 获取，handler 地址用 argaddr 获取（64 位地址，argint 会截断）；
  • n == 0 表示关闭，不需要额外的开关字段；
  • handler 地址可能为 0（实验说明提示 periodic 可能在地址 0），不能用它判断是否启用。

3. usertrap：定时器到点修改 epc

在 which_dev == 2 分支、yield() 之前处理：

if(p->interval > 0 && !p->in_handler){
  p->ticks++;
  if(p->ticks == p->interval){
    p->saved_tf = *p->trapframe;          // 第一步：整体备份
    p->trapframe->epc = p->handler;       // 第二步：修改 epc
    p->in_handler = 1;                    // 第三步：防重入
    p->ticks = 0;                         // 第四步：重新计数
  }
}

需要注意：handler 在用户态执行。内核只修改 epc；sret 返回用户态后，用户程序从 handler 的第一条指令开始执行，内核不会调用 handler。

4. sigreturn：整体恢复并返回 a0

uint64
sys_sigreturn(void)
{
  struct proc *p = myproc();
  *p->trapframe = p->saved_tf;   // 恢复全部用户寄存器（含 epc、a0）
  p->in_handler = 0;
  return p->trapframe->a0;       // 返回恢复出的 a0
}

必须返回 a0 的原因：kernel/syscall.c 分发完成后一定会执行：

p->trapframe->a0 = syscalls[num]();

如果返回 0，刚恢复的 a0 会立即被覆盖。

5. 完整流程

sigalarm(n, fn) → 保存 interval / handler，ticks 清零
定时器中断 → usertrap
  → interval>0 且 !in_handler：ticks++，到点后备份 trapframe、epc=handler、
     in_handler=1、ticks=0
  → yield → usertrapret → sret
handler 在用户态执行
handler 调用 sigreturn → 恢复 saved_tf → in_handler=0 → 返回 a0
  → sret 回到被定时器打断的那条指令

四、个人犯错记录与常见错误（重点）

实现过程中，容易出问题的地方集中在四类：类型与声明、合法输入的语义、状态重置、恢复顺序。

1. 头文件同时被 C 和汇编包含

现象：编译 trampoline.o 时报错：

kernel/riscv.h:365: Error: unrecognized opcode `static inline uint64'
kernel/riscv.h:366: Error: unrecognized opcode `r_fp()'
kernel/riscv.h:367: Error: junk at end of line, first unrecognized character is `{'

原因：riscv.h 以 #ifndef __ASSEMBLER__ 开头、以 #endif 结束；所有 C 代码必须位于守卫内部。若 r_fp() 被添加到文件末尾的 #endif 之后，而 trampoline.S 会 #include "riscv.h"，汇编器就会把 C 函数定义当成非法指令。

修正：将 r_fp() 移入守卫内部（例如 sfence_vma() 与 typedef uint64 pte_t; 之间）。宏（PGSIZE、PGROUNDDOWN）可以放在守卫外，因为预处理器会先行展开，汇编器看不到它们。

要点：头文件如果会被 .S 文件包含，C 声明必须放进 #ifndef __ASSEMBLER__。

3. argaddr 的第二个参数是输出参数

现象：

kernel/sysproc.c:103: error: passing argument 2 of 'argaddr' from
incompatible pointer type
kernel/sysproc.c:111: error: assignment to 'uint64' from 'uint64 *'
makes integer from pointer without a cast

原因：

uint64 *handler = 0;
argaddr(1, &handler);     // &handler 的类型是 uint64**

argaddr 的原型是 void argaddr(int n, uint64 *ip)，它会把用户传入的地址写入给定的 uint64 变量。

修正：

uint64 handler = 0;
argaddr(1, &handler);

要点：argint / argaddr 采用输出参数风格，传入的是存放结果的变量地址，而不是指针变量本身。

4. sigalarm(0, 0) 是合法的关闭操作

现象：alarmtest 运行到 test0 时内核 panic。

原因：在 sys_sigalarm 中加入了对参数合法性的过度检查：

if (n <= 0 || handler <= 0) {
    panic("interval <= 0 or handler <= 0\n");
}

test0 结尾会调用 sigalarm(0, 0) 关闭 alarm，slow_handler 中也会调用；同时 handler 地址本身也可能为 0。这两种情况都是合法输入。

修正：删除该检查。interval = 0 时，usertrap 中的 interval > 0 判断自然不会触发。

要点：不要对合法的用户输入使用 panic；panic 是内核的最后手段，不是参数校验工具。

5. tick 计数是每进程的，并且在两处需要重置

现象：修改 alarm 间隔后，alarm 有时不再触发。

原因：sigalarm 只更新了 interval，没有清零 ticks。例如残留 ticks = 1，新 interval = 1，下一次 tick 后 ticks = 2，之后只会继续增大，ticks == interval 永远不会成立。

修正：sigalarm 中设置 p->ticks = 0;，触发时同样清零。计数必须使用进程私有字段，不能使用全局 ticks——其他进程运行的时间不应计入。

要点：计数器要在"设置时"和"触发时"两处重置；使用相等判断时，残留值会导致永久错过。

6. sys_sigreturn 的返回值会覆盖恢复出的 a0

现象：test3 失败，报 a0 changed。

原因：sys_sigreturn 已将保存的 trapframe 拷回，但它自身返回 0；而 syscall() 分发完成后会执行：

p->trapframe->a0 = syscalls[num]();

恢复出的 a0 立即被覆盖。

修正：return p->trapframe->a0;，把恢复值作为系统调用的返回值返回。

要点：系统调用的返回值最终写入 trapframe->a0；恢复 a0 时，返回值必须等于恢复值。

7. 备份必须发生在修改 epc 之前

现象：handler 返回后没有回到被打断的代码，而是再次跳回 handler，形成循环。

原因：顺序错误：

p->trapframe->epc = p->handler;   // 先修改
p->saved_tf = *p->trapframe;      // 后备份：备份中的 epc 已是 handler 地址

修正：先备份，再修改：

p->saved_tf = *p->trapframe;
p->trapframe->epc = p->handler;

要点：备份保存的是"被打断那一刻"的现场，所有对 trapframe 的修改都必须发生在备份之后。

附：概念误区

错误理解正确理解
使用全局 ticks 计算 alarm 周期计数是每进程的，在 usertrap 的定时器分支递增；其他进程的时间不计入
保存 p->trapframe 指针作为备份指针指向同一页，handler 期间每次系统调用都会覆盖它；必须进行结构体拷贝
用 handler 地址是否为 0 判断 alarm 是否启用handler 可能位于地址 0；应使用 interval == 0 判断关闭
恢复时只拷贝 epc 和 a0必须整体恢复 trapframe，s0-s11 等寄存器也要恢复，否则 test1 会出现 i != j

五、总结

两个任务的机制可以各用一句话概括：

  • Backtrace：fp-8 是返回地址，fp-16 是上一帧 fp；PGROUNDDOWN 判断当前是否仍在同一个内核栈页；
  • Alarm：定时器到点先备份 trapframe、再修改 epc；sigreturn 整体恢复，并把恢复出的 a0 作为返回值。

实现时最重要的三个原则：

  1. 类型契约：extern 声明、函数指针数组、argaddr 的参数类型必须严格匹配；链接器不会做类型检查；
  2. 恢复的完整性：epc、a0、s0-s11 都要恢复，备份必须发生在任何修改之前；
  3. 状态与语义边界：interval == 0 表示关闭，handler 地址可以为 0，计数是每进程的且需要重置。
