AutoHotkey V2 零基础快速入门 Part 10：给路线回放添加高精度计时，理解累计延迟与路线一致性

承接 Part 9。上一章，我们给路线录制器添加了重复回放功能。这一章，我们进一步观察回放过程：计划什么时候发送按键，脚本实际什么时候准备发送，为什么两者会逐渐偏离，以及为什么不能为了追赶时间而牺牲路线。

一、Part 9 留下的问题

Part 9 的回放核心逻辑是这样的：

PreviousEventTime := 0
for Event in RouteEvents {
    Interval := Event.Time - PreviousEventTime
    Sleep(Interval)
    SendEvent("{" Event.ScanCode " down}")
    PreviousEventTime := Event.Time
}

它每次只等"相邻两个事件之间的时间差"。看起来没问题，但实测日志会变成这样：

事件 1:   DelayMs = 0
事件 2:   DelayMs = 16
事件 3:   DelayMs = 31
事件 4:   DelayMs = 47
...
事件 54:  DelayMs = 1000

每轮末尾晚约 1 秒，跑 25 轮就是 25 秒的累计偏差。Part 9 的文章里我们把这归因于"逐事件累加 Sleep 误差"。Part 10 要回答三个问题：

  1. 这个误差到底从哪来？
  2. 为什么"等到绝对时刻"能消除它？
  3. AHK v2 里怎么把"等到绝对时刻"写得准、写得稳、还能随时按 F12 停？

二、误差从哪来：Sleep 不是精确的

2.1 Windows 的计时器精度

Windows 默认的系统计时器精度是 15.6ms（1/64 秒）。你调用 Sleep(16)，实际可能睡 15ms，也可能睡 31ms，取决于当前 tick 落在哪里。

Sleep(16)   ; 实际耗时可能是 15ms 或 31ms

即使你调用 timeBeginPeriod(1) 把精度提到 1ms，Sleep(1) 实际也常是 1~2ms，而且有调度开销。

你可以把它理解成：你让程序“休息 16 毫秒”，但系统不一定能准时叫醒它。

想象你在等公交车：

  • 你希望 16 分钟后出发。
  • 但公交车不是随到随走，而是隔一段时间才来一班。
  • 到了你想出发的时间，如果车还没来，你就得继续等。

2.2 误差会累积

相对调度的每个间隔误差，会叠加到下一个间隔上：

计划间隔: 100  100  100  100
实际间隔: 115  115  115  115
实际时刻: 115  230  345  460   ← 误差线性增长

54 个事件，每个多约 18ms，累积起来正好约 1 秒。这就是日志里 DelayMs 从 0 涨到 1000 的原因。

2.3 为什么不能简单"少睡一点"

有人会想：那我 Sleep(Interval - 10) 不就行了？

不行。因为误差不是固定 10ms，它随系统负载、tick 位置波动。你减 10ms，可能这次刚好，下次又多了 5ms，再下次少了 3ms。开环补偿治标不治本。

正确的做法是闭环：每个事件都对准一个绝对时刻，晚了就少等，早了就多等。

三、绝对时间调度：每个事件对准自己的时刻

3.1 思路

路线里每个事件记录的是"相对于路线起点的绝对时间"：

事件 1: 1000ms
事件 2: 1688ms
事件 3: 5813ms

回放时，先记下本轮开始的时刻 RoundStartMs，然后对每个事件计算它的绝对目标时刻：

TargetMs = RoundStartMs + Event.Time

然后一直等到 TargetMs，而不是等"和上一个事件的差值"。

3.2 误差不再累积

计划时刻: 100  200  300  400
实际时刻: 115  200  315  400
误差:     +15    0  +15    0

第 1 个事件晚了 15ms，第 2 个事件发现"已经 115ms 了，目标 200ms，再等 85ms 就行"，于是准时。第 3 个又晚 15ms，第 4 个又追回来。误差有界，不增长。

3.3 代码

PlayOneRouteRound() {
    RoundStartMs := QpcMs()


for EventIndex, Event in RouteEvents &#123;
    PlannedTime := Round(Event.Time * PlaybackSpeed)
    TargetMs := RoundStartMs + PlannedTime

    ; 等到绝对时刻
    PreciseSleepUntilMs(TargetMs)

    SendEvent("&#123;" Event.ScanCode " down&#125;")
&#125;



&#125;

注意：RoundStartMs 只在每轮开始时取一次，轮内所有事件都基于它计算目标时刻。这样某个事件晚了，不会影响后面事件的目标时刻。

四、高精度计时：为什么不用 A_TickCount

4.1 A_TickCount 的局限

A_TickCount 返回系统启动以来的毫秒数，够用，但：

  • 精度受系统计时器影响，默认 15.6ms；
  • 它是整数毫秒，短间隔事件（16ms）的舍入误差占比很大；
  • 不适合做"毫秒级对准"。

4.2 QueryPerformanceCounter

Windows 提供高精度计时器 QueryPerformanceCounter（QPC），精度通常是微秒级。AHK v2 通过 DllCall 调用：

InitQpc() {
    global QpcFreq
    DllCall("QueryPerformanceFrequency", "Int64*", &QpcFreq)
}


QpcMs() &#123;
    global QpcFreq
    DllCall(“QueryPerformanceCounter”, “Int64*”, &Count)
    return Count / QpcFreq * 1000
&#125;

QueryPerformanceFrequency 返回每秒的计数频率（比如 10,000,000），QueryPerformanceCounter 返回当前计数。两者相除就是秒，乘 1000 就是毫秒。

4.3 为什么先除后乘

return Count / QpcFreq * 1000

而不是：

return Count * 1000 / QpcFreq   ; 不推荐

因为 Count 是 64 位整数，乘 1000 可能溢出，或者先转成浮点丢精度。先除后乘，中间结果是浮点，安全。

4.4 初始化要检查失败

DllCall 可能失败，QpcFreq 可能是 0。除以 0 会抛异常，所以在初始化时检查：

if !Freq
    throw Error("QueryPerformanceFrequency 返回 0，无法进行高精度计时。")

回放开始前调用 InitQpc()，失败就取消回放并提示，而不是跑到一半崩掉。

五、Sleep 精度：timeBeginPeriod 与最后几毫秒

5.1 临时提高系统计时器精度

DllCall("winmm\timeBeginPeriod", "UInt", 1)

这行告诉 Windows："接下来一段时间我需要 1ms 精度的计时器。" 调用后，Sleep(1) 实际约 1~2ms，而不是 15.6ms。

用完要还，否则会影响系统功耗和其他程序：

DllCall("winmm\timeEndPeriod", "UInt", 1)

脚本里用 TimePeriodSet 标志记录是否设置过，在 CleanupBeforeExit 里恢复。

5.2 等到目标时刻的写法

PreciseSleepUntilMs(TargetMs) {
    global IsRoutePlaying


while IsRoutePlaying &#123;
    Remaining := TargetMs - QpcMs()

    if Remaining &lt;= 0
        return true

    if Remaining &gt; 3 &#123;
        Sleep(Min(5, Max(1, Floor(Remaining) - 2)))
    &#125; else &#123;
        Sleep(1)
    &#125;
&#125;

return false



&#125;

几个设计点：

为什么大块时间用 Sleep(5) 而不是 Sleep(Remaining)？ 因为 Sleep(Remaining) 可能睡过头，醒来发现已经超过目标。每次睡一小段，醒来重新检查剩余时间，更稳。

为什么最后 3ms 用 Sleep(1) 而不是纯忙等？ 纯忙等（while QpcMs() < TargetMs）会占满 CPU，AHK 的消息循环停止，F12 热键、窗口焦点检查都无法及时响应。Sleep(1) 在 timeBeginPeriod(1) 下精度足够，又能让出 CPU。

为什么循环条件里有 IsRoutePlaying？ 这样 F12 紧急停止时，IsRoutePlaying 变成 false，等待循环立即退出，不会卡在 Sleep 里。

5.3 绝对调度的好处：不追求单次极致精度

因为每个事件都对准绝对时刻，单次晚 10ms 不影响下一个事件。所以 PreciseSleepUntilMs 不需要精确到 1ms 以内，只要"平均误差小、不累积"就够了。这让实现可以兼顾精度和响应性。

六、可中断等待：轮间等待与 F12

6.1 轮间等待不能直接用 Sleep

Part 9 的轮间等待是：

Sleep(PlaybackRepeatIntervalMs)

问题是：Sleep(8000) 期间，F12 按了也没用，脚本要等 8 秒才响应。

6.2 可中断等待

InterruptibleSleep(DurationMs) {
    global IsRoutePlaying


if DurationMs &lt;= 0
    return IsRoutePlaying

EndTick := A_TickCount + DurationMs

while A_TickCount &lt; EndTick &#123;
    if !IsRoutePlaying
        return false

    Remaining := EndTick - A_TickCount
    Sleep(Min(Remaining, 20))
&#125;

return IsRoutePlaying



&#125;

思路：把长等待切成 20ms 的小段，每段醒来检查 IsRoutePlaying。F12 把 IsRoutePlaying 设为 false，下一个 20ms 内就退出。

为什么用 A_TickCount 而不是 QPC？ 轮间等待不参与事件计划时间，精度要求低，A_TickCount 足够，而且 InterruptibleSleep 本身会被调用很多次，用更轻量的 A_TickCount 更合适。

6.3 两种等待的分工

函数用途计时器精度要求
PreciseSleepUntilMs轮内事件对准QPC高
InterruptibleSleep轮间等待、倒计时A_TickCount低

这个分工很重要：不是所有等待都需要高精度，轮间 8 秒等待差 5ms 完全无所谓。

七、诊断日志：让误差可见

7.1 三个时间字段

PlannedTime  := Round(Event.Time * PlaybackSpeed)
ActualTime   := Round(QpcMs() - RoundStartMs)
DelayMs      := ActualTime - PlannedTime
  • PlannedTime：按路线和速度倍率算出的计划相对时刻；
  • ActualTime：实际发送前，相对于本轮开始的时刻；
  • DelayMs：实际减计划，正数表示晚了，负数表示早了。

7.2 日志只写内存，不写磁盘

AppendPlaybackLog(...) {
    global PlaybackLogRows
    PlaybackLogRows.Push({...})
}

每个事件都写磁盘会显著放大计时误差。正确做法是：事件之间只往数组里 push，回放全部结束后一次性写 CSV。

7.3 日志能告诉你什么

  • DelayMs 随事件序号增长 → 相对调度，误差累积；
  • DelayMs 在固定范围抖动 → 绝对调度，误差有界；
  • GameActive = 0 → 发送时窗口失去焦点，回放被中断；
  • 某个事件 DelayMs 异常大 → 那个位置系统负载高，或 Sleep 被拉长。

八、错误处理：不让一次异常毁掉整轮日志

8.1 try / catch / finally

回放主循环用 try ... catch ... finally 包住：

try {
    Loop PlaybackRepeatCount {
        ...
        if !PlayOneRouteRound()
            break
        ...
    }
} catch as Err {
    MsgBox("轮次：" CurrentPlaybackRound "`n错误：" Err.Message ...)
} finally {
    IsRoutePlaying := false
    ReleaseAllRecordedKeys()
    ReleaseCommonGameKeys()
    try SavePlaybackLogToCsv()
}

finally 是关键：无论正常结束、F12 中断、失焦、还是抛异常，都执行清理和日志保存。这样即使第 13 轮出错，前 12 轮的诊断日志还在。

8.2 单事件级别的错误定位

PlayOneRouteRound 里每个事件包了 try/catch：

try {
    ...
} catch as Err {
    throw Error(
        "第 " CurrentPlaybackRound " 轮第 " EventIndex " 个事件出错。"
        . "`n按键：" Event.Key " / 动作：" Event.Action
        . "`n原始错误：" Err.Message
    )
}

这样报错时能看到"第几轮、第几个事件、哪个键"，而不是只有一行"DllCall 失败"。

8.3 资源清理

CleanupBeforeExit 在脚本退出时执行：

if TimePeriodSet {
    try DllCall("winmm\timeEndPeriod", "UInt", 1)
    TimePeriodSet := false
}

恢复系统计时器精度，释放按键，保存日志。自己设置的状态，自己负责恢复。

十、小结

这一篇讲了什么

  1. Sleep 不精确，相对调度的误差会线性累积；
  2. 绝对时间调度让每个事件对准自己的目标时刻，误差有界；
  3. QPC 提供微秒级计时，替代 A_TickCount；
  4. timeBeginPeriod(1) 临时提高系统计时器精度，用完要 timeEndPeriod(1)；
  5. PreciseSleepUntilMs 大块 Sleep + 最后 Sleep(1)，兼顾精度和响应性；
  6. InterruptibleSleep 把长等待切段，保证 F12 能及时停；
  7. 诊断日志只写内存，结束后一次性落盘；
  8. try/catch/finally 保证异常时也保存日志、释放按键、恢复计时器精度。
