从「本地能跑」到「敢给别人看」：个人项目的 12 项生产就绪清单

改了邮箱，部署完 curl 是新内容，浏览器里还是旧的——因为 gzip 静态文件没重建。 顺着这次事故，我把个人站点的可访问性、可维护性、可靠性拆成 12 项，逐项补齐并真的验证。 全文约 1300 字，附 6 个可复制的运维脚本。

一、一个很小的翻车

晚上七点，我改了简历站的联系邮箱，部署完用 curl 一看是新邮箱，收工。

十分钟后打开浏览器——还是旧邮箱。

原因不复杂：nginx 开了 gzip_static on，index.html.gz 是三天前生成的。文件确实传上去了，但用户拿到的还是旧的压缩文件。

这件事让我意识到一个问题：我一直用「功能跑通了」当作「做完了」。但下面三件事，从来没被当成验收标准：

  1. 别人能访问到吗——DNS、证书、缓存旧内容
  2. 改得动、说得清吗——配置只在服务器上、改坏了回不去
  3. 坏了知道吗、丢了能恢复吗——备份没验证过、告警没响过

只要有一个答不上来，项目就还在「裸奔」。

二、12 项检查表

A. 可访问性（别人能不能打开）

1）域名解析：A / MX / TXT（SPF）各司其职。

dig +short A   example.com
dig +short MX  example.com
dig +short TXT example.com   # TXT 允许多条共存，不会覆盖 SPF

2）HTTPS + 自动续期：证书失败等于全站不可用，而且不会提前通知你。除了 certbot.timer，还要有到期告警：<21 天警告，<7 天严重。

3）内容正确性：凡是会生成两份产物的部署，两条路径都要验证。

curl -s https://example.com/ | grep -c 'MARKER'
curl -s -H 'Accept-Encoding: gzip' https://example.com/ -o /tmp/r.gz
gunzip -c /tmp/r.gz | grep -c 'MARKER'   # 浏览器实际拿到的

4）被搜到：写完文章不提交，等于没写。sitemap.xml + robots.txt 声明，再去站长平台提交；新文章用 IndexNow 主动推送（几秒就能通知 Bing 等）。

B. 可维护性（改得动、说得清）

5）配置进版本控制：nginx 配置、systemd 单元、维护脚本，都进 git。数据能从备份恢复，但配置只能靠记忆重写。

6）一键部署：一条命令、幂等、失败自动退出。部署脚本最后一定要有一条验收请求，curl -fsS 拉不到就 exit 1。

7）可回滚：部署前留一份带时间戳的副本，回滚就是覆盖回去 + reload，30 秒搞定。

8）重建文档：写清「从裸机到全功能」的每一步，包括容易忘的细节（证书怎么续、gzip 要重建、有哪些定时任务）。

C. 可靠性（坏了知道、丢了能恢复）

9）异地备份：同一份备份同时写两个云。这里最容易踩的坑不是代码，而是物理距离——

同一个脚本、同一台机器，上传 1.6 MB：

目标耗时
广州 ap-guangzhou≈120 秒，经常超时
美东 na-ashburn0.95 秒

我一开始想用「加超时 + 重试」解决，治标不治本。网络慢先怀疑物理距离，先测一条命令的耗时，比调参数有用得多。

10）恢复演练：backup success 天天有，但你可能从没解包过。演练要真把服务跑起来：拉副本 → sha256 比对 → 解包 → PRAGMA integrity_check → 跑一次真实查询 → 起服务访问页面 → nginx -t 校验配置。

这次演练最有价值的不是「一切正常」，而是发现数据库里用户收藏的数据根本没进备份包。没演练过，你永远不会知道漏了什么。

11）告警 + 心跳：这是两条不同的线。

通道回答的问题
告警（Telegram）「内容坏了没」——检查发现异常时发
心跳（healthchecks）「检查还在跑吗」——到点没报平安也发

心跳实现很小，做成 systemd 包装器即可，主脚本一行都不用改：

#!/bin/bash
curl -fsS -m 10 "https://hc-ping.com/$UUID/start" || true
"$@"; RC=$?
if [ $RC -eq 0 ]; then curl -fsS -m 10 "https://hc-ping.com/$UUID";
else curl -fsS -m 10 "https://hc-ping.com/$UUID/fail"; fi
exit $RC

12）状态可见：一个公开状态页，展示定时任务上次运行时间、服务状态、证书剩余天数、备份时间、磁盘内存、站点响应时间。数据每 5 分钟刷新。

设计上把采集和展示分开：脚本输出 JSON，页面 fetch 渲染，改样式不用碰采集逻辑。

三、成本：0 元还是 10 美元

项目费用
域名¥70/年
服务器GCP 免费层
HTTPSLet's Encrypt，0
双云备份两家免费额度，0
告警 + 心跳自建 + 免费版，0
云数据库≈$10/月 ← 唯一真金白银

整套可靠性体系可以做到接近 0 成本，真正花钱的永远是「托管数据库」这类省事的东西。

四、最值钱的三个坑

  1. 告警从没响过 = 阈值设成了不可能触发的值，等于没配。每条告警都要故意触发一次。
  2. 备份从没解包过 = 你不知道它能不能恢复，也不知道漏了什么。
  3. 告警只有一条通道 = 那条通道挂了，你就彻底静默。加心跳，回答「检查本身还在不在跑」。

五、最后

这 12 项里，没有一项的技术难度超过「写个 CRUD」。难的是承认「跑通了」不等于「做完了」。
